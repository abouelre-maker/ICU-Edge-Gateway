# A7 — Patient identity and message type

**Status:** PROPOSAL — UNSIGNED, pending clinical safety review (HD-E4).

## Hazardous situation
- Only the first PID-3 repetition was read, with no identifier-type handling.
- An empty PID-3 became `"UNKNOWN"`, merging distinct patients' data under one identity.
- MSH-9 was never checked, so an ADT message was processed as vitals.
- Non-standard MSH-2 encoding characters were silently mis-split.
- HL7 escape sequences were not decoded.

## Change (risk control, proposed)
- All PID-3 repetitions are read from the raw segment:
  - one identifier ⇒ used;
  - several ⇒ the single `MR`-typed one;
  - otherwise, or if none ⇒ `AMBIGUOUS_PATIENT_ID`, which forces INCOMPLETE.
  - `"UNKNOWN"` is kept as the placeholder, but it can never carry a score.
- MSH-9 ≠ `ORU^R01` ⇒ `UNSUPPORTED_MESSAGE_TYPE` (forces INCOMPLETE; the MLLP listener answers AR — see A8).
- `message_control_id` (MSH-10) and `message_type` are exposed on the parse result, for A8.
- Non-standard MSH-1/MSH-2 ⇒ explicit `ValueError` (HTTP 422 / MLLP reject), never a mis-split.
- `\F\ \S\ \T\ \R\ \E\` are decoded in the patient identifier and the control ID.

## Open
- The assigning authority is not yet part of the identity key. Two facilities' `MR` numbers could still collide. This belongs with the Phase 3 identifier/`Patient.id` work (H-05).
