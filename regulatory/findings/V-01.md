# V-01 — Vendor OBX code tables are invented, not sourced

**Status:** PROPOSAL — UNSIGNED. Closed only as *data-driven + provenance-labelled*.
Real closure needs a de-identified real sample (HD-E3).

## Hazardous situation
The adapter shipped a hard-coded table of proprietary OBX-3 codes attributed to
five monitor vendors, and its docstring claimed support for those vendors. The
mappings were inferred; none came from a vendor interface specification or from
observed traffic. A wrong mapping feeds a different physiological quantity into
NEWS2 (see A5).

## Change (risk control, proposed)
- The table moves to `src/infrastructure/adapters/vendor_codes.json`: 31 records, generated mechanically from the previous dict.
- Each record has `code`, `system`, `maps_to`, `provenance`, `source_ref`. Every entry is `provenance: inferred-UNVERIFIED`, `source_ref: TODO-VERIFY`.
- A strict loader (`vendor_codes.py`) rejects:
  - unknown or extra fields, and empty values;
  - a provenance outside {vendor-spec, observed-traffic, inferred-UNVERIFIED};
  - a `maps_to` that is not a VitalSignType;
  - duplicate codes.
  A defective table stops the adapter from importing, so the service cannot start with a half-valid table.
- The adapter docstring no longer names vendors or models. It states that the mappings are inferred. The LOINC table comment no longer claims "validated against NLM VSAC".

## Open
- Documentation and commercial claims of multi-vendor support are removed in Phase 7 (R-01/R-07) and are already listed as NOT TRUE in `CLAIMS_CANONICAL.md`.
- MSH-3 vendor *detection* (`_VENDOR_SUBSTRINGS`) is still inferred. It only labels the Device resource and warning text; it does not map codes.
